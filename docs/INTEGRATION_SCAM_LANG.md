## 1. 來源專案分析

### 1.1 它是什麼

投資反詐與交易統計工具。核心能力分成兩塊，性質差異很大：

| 模組 | 輸入 | 產出 | 與司法專案的關聯 |
|---|---|---|---|
| `core/antiscam/` | **純文字** | 詐騙話術風險等級（極高／高／中／低／資訊不足）＋逐句證據標註＋反詐金句 | **直接可用**——詐騙類民事／刑事案件正是本專案業務 |
| `core/` 其餘（統計、載入、券商、策略） | **交易紀錄檔** | 勝率、期望值、顯著性檢定、倖存者偏差分析 | 交易紀錄非法律案件常見資料 |

### 1.2 關鍵技術前提

**核心零外部依賴**（`pyproject.toml` 宣告 `dependencies = []`），只用 Python 標準函式庫。
`openpyxl`、`backtrader`、`vectorbt`、`Pillow` 全部是選用 extras。

這一點決定了整合難度：**反詐掃描器不需要任何第三方套件**。

### 1.3 兩個入口的介面契約

```python
# 純文字掃描
scan_text(text: str) -> TextScanResult
render_scan(r: TextScanResult) -> str          # 可讀報告

# 檔案分析
load_trades(path, *, market_hint, auto_estimate_costs, field_overrides) -> TradeLog
analyze_file(path, *, market_hint, framework, auto_estimate_costs, n_bootstrap) -> AnalysisResult
```

`TextScanResult` 主要欄位：

```python
risk_level: str            # 極高／高／中／低／資訊不足
headline: str
distinct_categories: int   # 命中相異話術類別數（主要判準）
hits: list[Hit]            # 每筆含 phrase/category/negated/sentence/reason
negated_hits: list[Hit]    # 被否定語境濾掉者
is_discussion: bool        # 是否為「討論這是詐騙嗎」的反詐教育文
advice: list[str]
annotated_sentences: list[tuple[str, list[str]]]
```

`AnalysisResult.as_dict()` 主要欄位：
`source` / `markets` / `verdict` / `stage{code,title,reason,next_actions}` /
`profile` / `out_of_sample` / `tag_verdicts` / `counterfactual` / `follow_guru`

### 1.4 移植成本量化

| 檔案 | 行數 | 是否需要 |
|---|---|---|
| `core/antiscam/patterns.py` | 132 | **需要**（話術詞庫） |
| `core/antiscam/text_scanner.py` | 783 | **需要**（掃描邏輯） |
| `core/antiscam/signals.py` | 81 | 視整合深度而定 |
| `core/metrics/performance.py` | 403 | 交易統計，本專案不需要 |
| `core/verdict/statistics.py` | 376 | t 檢定／bootstrap，本專案不需要 |
| `core/ingest/loader.py` | 1122 | 交易紀錄載入，本專案不需要 |

**只做反詐掃描＝915 行；連統計一起做＝3,368 行。**

### 1.5 來源專案值得直接吸收的兩項

**(a) 簡繁正規化對照表**

`text_scanner.py` 註解記載：

> 實測簡體版核心話術原本 0 命中、判「低風險」,**完全繞過偵測**

他們踩過與本專案相同的坑（簡體繞過），並在詞庫比對前先做 `str.translate` 簡繁正規化。
該對照表已在他們的語料上驗證過，**建議直接移植**（含他們刻意排除異體字的判準）。

**(b) 設計原則值得遵循**

`text_scanner.py` 開頭列了六條限制，其中三條與本專案的治理原則直接對齊：

1. **不給假百分比**——只給序數等級。「87.3% 是詐騙」未經語料校準，是假精準。
2. **不用關鍵字密度**——密度可被稀釋，改用「命中幾種相異類別」。
3. **不做統計顯著性檢定**——單一則文字沒有抽樣模型，p 值無定義。

**第 1 點與本專案「不得過度宣稱」完全一致**，移植時應保留。

## 2. 整合設計

### 2.1 位置：案件分析流程內嵌（依你選擇）

**執行點**：`POST /api/workflow/execute` → `step 1: RouterNode 評估`
（`server/routes/unifiedWorkflow.ts:676`）

**為什麼選在這裡**：`universalTriage` 已經在做案件類型判斷，
「輸入是否含投資詐騙話術」是同一層級的判斷，放在同一處最自然，
且不增加額外呼叫往返。

**建議執行序**（在 `runRouterNode` 之後、其餘節點之前）：

```
1. 輸入檢查與去識別化（既有流程）
2. RouterNode 評估（既有）
3. ★ 新增：scamLanguageScan(userNarrative)   ← 純本地運算
4. 後續節點（既有）
5. 回應中加入 scamLanguage 欄位
```

第 3 步是**同步的純文字運算**（無 AI 呼叫、無網路請求），
預估 <10ms，不會增加現有的 12–27 秒延遲。

### 2.2 資料流

```
使用者貼上案件事實
      ↓
去識別化（既有，剝除身分證／電話）
      ↓
★ 詐騙話術掃描（新增）
   ├─ NFKC 正規化（全形→半形）
   ├─ 移除零寬字元（U+200B/200C/200D、BOM）
   ├─ 簡→繁 1:1 等長替換（座標不位移）
   ├─ 詞庫比對（多類別）
   ├─ 否定語境濾除（雙向視窗）
   └─ 討論守門（反詐教育文降級）
      ↓
風險等級 + 命中句 + 原因
      ↓
併入既有分析結果回應
      ↓
前端以既有元件樣式呈現
```

### 2.3 API 契約

**不新增端點**（在既有回應中加欄位）：

```jsonc
// POST /api/workflow/execute 回應增量
{
  "data": {
    // …既有欄位不變…
    "scamLanguage": {
      "riskLevel": "高",              // 極高／高／中／低／資訊不足
      "headline": "輸入含多項投資詐騙話術特徵",
      "distinctCategories": 3,          // 命中相異類別數
      "isDiscussion": false,            // 是否為反詐討論文
      "hits": [
        {
          "sentence": "老師說保證獲利⋯⋯",
          "matchedText": "保證獲利",
          "category": "保證獲利話術",
          "reason": "保證獲利是投資詐騙的典型特徵",
          "negated": false
        }
      ],
      "advice": ["⋯⋯"]
    }
  }
}
```

**保持不變**：所有既有欄位、所有既有閘門（引用檢核、繁體檢核、fail-closed）。

### 2.4 前端呈現

在案件分析結果面板新增一區塊，位置緊接「初步分析（待查驗）」之後：

- 風險等級徽章（極高／高／中／低／資訊不足）
- 命中句列表（可逐句核對）
- 反詐提醒

**必須遵守的呈現原則**（沿用本專案治理規則）：

1. 明確標示「本結果為話術特徵偵測，非司法鑑定」
2. 引用官方管道：165 全民防騙網、金管會證期局
3. 不呈現任何未經語料校準的百分比
4. 標示「仍需人工核對原始對話」

## 3. 上傳功能設計

你未指定上傳類型，我列出本專案情境下**真正合理**的三種與建議。

### 3.1 現況

**本專案目前沒有伺服器端上傳中介層**（無 multer／formidable）。
前端雖有 `<input type="file">`，但都在瀏覽器端解析（PDF 讀文字），
檔案不經過伺服器。

### 3.2 三種選項

| 選項 | 實作方式 | 伺服器端需求 | 建議 |
|---|---|---|---|
| **A. 貼上文字** | 既有 textarea，零新增 | 無 | **建議預設**——覆蓋多數情境，成本最低 |
| **B. 上傳圖片（對話截圖）** | 瀏覽器端 Canvas 讀圖 → 使用者確認文字 → 送掃描 | 無 | 可行。**不建議**伺服器端 OCR（需 Pillow + pytesseract，繁中準確率不穩） |
| **C. 上傳 PDF（書狀／裁判書）** | 既有 PDF 解析器已存在 | 無 | **建議**：書狀與裁判書的 PDF 是本專案既有場景 |

### 3.3 建議方案

```
┌─ 上傳區 ────────────────────────────┐
│  [貼上文字]  [上傳圖片]  [上傳 PDF]    │
└─────────────────────────────────────┘
```

**三種最終都走同一條路徑**：取得文字 → 去識別化 → 話術掃描。

- **圖片**：瀏覽器端讀圖 → 顯示辨識文字讓**使用者逐字確認或修正** → 才送掃描。
  不直接對 OCR 結果做判定（誤判會被當成法律事實）。
- **PDF**：沿用專案既有解析器。

**這樣做的好處**：完全不需要新增伺服器端上傳中介層，
也不需要處理檔案落地、清理、大小限制等一整類安全問題。

若日後確實需要伺服器端接收檔案（例如大量批次），再評估加入
multer + 嚴格的型別與大小白名單。

## 4. 風險評估

| 風險 | 等級 | 緩解 |
|---|---|---|
| **誤判把正常案件當詐騙** | **高** | 沿用其「討論守門」；結果明確標示為「線索」非「認定」；只給序數等級 |
| **漏判真實詐騙** | 中 | 詞庫覆蓋率有限，必須在介面說明「僅供線索參考」 |
| 移植後行為與原版不一致 | 中 | 需建立**對照測試集**：同一批中英文文本，比對 Python 與 TS 輸出 |
| 商業授權 | 低 | MIT 可商用，只需保留版權聲明 |
| 延遲增加 | 低 | 純本地運算，預估 <10ms |
| 引入檔案上傳的攻擊面 | — | **採用建議方案則完全迴避**（見 3.3） |

### 最大風險的處理

誤判是唯一需要認真對待的問題。本專案已有類似的治理經驗——
「零引用的書狀被呈現為可遞狀」曾是真實缺陷。

**設計約束**：掃描結果**不得**進入任何交付文件的內容，
只作為「案件性質線索」顯示在分析面板，
且必須與法律結論視覺上明確區隔。

## 7. 未納入本次範圍

以下來源專案的功能**不建議**整合，理由如下：

- **交易統計、期望值、顯著性檢定**：需要交易紀錄，與法律案件無關
- **倖存者偏差分析**（`survivorship.py`）：同上
- **假績效鑑識**（`forensics/`）：同上
- **自動化交易 scaffold**（`core/scaffold/`、`core/broker/`）：
  **明確排除**——本專案是法律文件產製系統，不應產出可送單的交易程式。
  即便原作者設計了多層安全閘門，引入此能力本身超出本專案目的。

若日後有「投資糾紛案件需要統計鑑識」的需求，可再評估統計模組；
交易與券商部分則應永久排除。
